# AGENTS.md

Guidance for coding agents and contributors working in this repository.

## What this is

`ocis-agent` is an always-on personal agent for ownCloud Infinite Scale (oCIS): a Go
sidecar (`backend/`) next to oCIS plus an oCIS Web extension (`frontend/`, `web-app-agent`).

Design notes are maintained outside the repository, so this file and the code state
everything a contributor needs.

## Layout

- `backend/` Go module `github.com/owncloud/ocis-agent/backend` (`cmd/`, `internal/`)
- `frontend/` Vue 3 + TypeScript extension, built with `@ownclouders/extension-sdk`
- `docker-compose.yml` + `dev/` dev stack (oCIS + nginx TLS proxy), run from the repo root.
  The host port is `OCIS_DEV_PORT` (default 9200, set in `.env`), so the stack is at
  `https://localhost:$OCIS_DEV_PORT`. Changing it after the first start needs `docker compose down -v`.
  Demo user `einstein` / `relativity`; the extension manifest is served at `/assets/apps/agent/manifest.json`.
- `Dockerfile` (sidecar image: static binary, uid 10001, `/data` volume, read-only root works, health check on
  `:9300/agent-api/healthz`) and `deploy/docker-compose.example.yml` (sidecar beside an existing oCIS; keep its
  `stop_grace_period` >= `AGENT_SHUTDOWN_DRAIN` + 15s and the master key in a 0600 env_file)

## Commands

- `make backend-vet backend-test` Go vet, gofmt check, unit tests
- `make frontend-test frontend-build` Vitest and the production extension build; `pnpm build:w` (in `frontend/`) rebuilds `dist/` on change for the dev stack, which mounts it
- `make license-check` REUSE lint (must pass before every commit)
- `make dev-up dev-down` local oCIS stack (after the first `make dev-up`, `docker compose up -d` also works; a fresh clone first needs `dev/certs` and `frontend/dist`, which `make dev-up` creates, and creating them via a bare compose run leaves root-owned bind-mount directories on Linux); `make sidecar` runs the sidecar against the dev stack (dev master key and database persist in `backend/bin/data`; delete it to reset local state; never use that key outside local development); `make spike` runs a probe of app-token renewal, SSE events and WebDAV preconditions against the dev stack
- `ocis-agent backup <dest>` writes a consistent snapshot of the database (`VACUUM INTO`, safe while the sidecar runs) to a new file (never overwrites; mode 0600; synced, then verified by integrity check and schema version); it reads only `AGENT_DATA_DIR`/`AGENT_SQLITE_PATH`, never the master key, and refuses a missing database
- `make integration-test` runs the end-to-end test (`backend/internal/integration`; the scenarios have the build tag `integration`, the harness rules and fakes run in `make backend-test`) against the running dev stack: it logs in as `einstein` through the oCIS IdP, starts its own sidecar (built binary, temporary data dir and master key, free loopback ports, a scripted fake model) and drives the REST API like the browser. It never touches `backend/bin/data` or a sidecar you run yourself, never calls revoke-all and deletes only what the rules in `rules_test.go` select: tokens of its own sidecar instance (its random label prefix, minus labels that existed before), files it created (`ocis-agent-it-*` at the drive root, its `notes/ocis-agent-it-*.md`, the `/.ocis-agent/README.md` its enrolment created, only while unchanged) and their trash entries, and memory folders it created while they are empty (their folder entries stay in the trash). A lock in `$TMPDIR/ocis-agent-it/` (a directory of your own with mode 0700, else the run refuses) allows one run at a time. A run interrupted with Ctrl-C, SIGTERM or SIGHUP cleans up on the way out (a second signal stops it at once); one killed hard (SIGKILL, the `go test` timeout) leaves its sidecar process, token and files until the next run cleans up from `$TMPDIR/ocis-agent-it/state.json`, which records the token prefix right after the sidecar starts, before the first enrolment, and which the next run refuses if it names anything a run never creates (by hand: stop the `ocis-agent` process started from `$TMPDIR/ocis-agent-it-*`, delete einstein's app tokens with the prefix recorded there (`GET` and `DELETE /auth-app/tokens?token=<listed hash>`), the `ocis-agent-it-*` files, then the state file). Without the stack `go test` skips the scenarios (with how to start it), and the make target says so and fails

## Conventions

- Test first. Every behavior change has a failing test before the code that fixes it.
- Go: standard library first, no cgo, errors wrapped with context and never containing secrets.
- Commits and PR titles are Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`,
  `refactor:`, `test:`, `ci:`, `perf:`; breaking changes use `!` or a `BREAKING CHANGE:`
  footer). The changelog is generated from them, so write subjects as changelog entries.
- Sign off (`git commit -s`) and GPG-sign every commit.
- Licensing is declared centrally in `REUSE.toml` (Apache-2.0). Do not add per-file headers.
  There is no hand-written changelog file.
- A local oCIS checkout (if present) is a read-only reference; never modify it.

## Invariants (do not break)

1. The sidecar's HTTP API lives under `/agent-api/`. Never serve or route `/agent/`: those
   are the extension's UI routes and must reach oCIS Web.
2. The approval gate and all policy are enforced server-side, in Go, from the database.
   File contents, file names, memory, connector output and model text are untrusted data;
   no text may change policy, and destructive or outward actions always need approval.
3. `AGENT_MASTER_KEY` (base64, 32 bytes) comes only from the environment. The sidecar refuses
   to start without it. Never log, print or commit app tokens, the master key or LLM keys.
4. The sidecar talks to oCIS only through public HTTP APIs (Graph, WebDAV, auth-app, SSE).
   No changes to oCIS itself.
5. Approvals, policy changes, enrolment, incident revoke and unenroll require the user's OIDC token,
   never the agent's app token. Only renewing or rotating the agent's own token may use the app token.

## Verified oCIS behaviour (measured on the dev stack; identical on oCIS 8.2.1 and 9.0.0-rc.1, the pinned tag)

- `POST /auth-app/tokens` authenticated with an app token itself succeeds and returns a usable new token, and tokens are
  independent (deleting one leaves the others valid). A stolen token can therefore renew itself whatever the sidecar does.
- Policy for v1: the sidecar renews its own token in the background (below 50% of the TTL, default `AGENT_TOKEN_TTL`
  72h): create with the current token and a unique label `ocis-agent-<instanceId>-<nonce>`, verify with Graph `/me`, swap
  transactionally, then delete the old token. Safeguards: unenroll deletes every token with this instance's label prefix;
  a separately confirmed incident revoke deletes all of the user's app tokens; every sweep lists the tokens
  and pauses the agent (`token_anomaly`) on an unknown token with our prefix; the agent pauses itself (`dormant`) when
  the user has not been seen for `AGENT_DORMANCY_DAYS` (default 30). Never log or audit token or hash values.
- `DELETE /auth-app/tokens?token=` needs the hash returned in the `token` field of `GET /auth-app/tokens` (find it by
  label and created date), not the plaintext token (plaintext gives 500); with the hash it returns 200 and the token then gets 401. An already-deleted or unknown hash also returns 500 (not 404), so confirm a delete via the token list.
- The SSE endpoint `/ocs/v2.php/apps/notifications/api/v1/notifications/sse` accepts app-token Basic auth and emits
  `folder-created`, `postprocessing-finished` (upload), `item-renamed` (move) and `item-trashed` (delete) for the
  user's file operations; the data carries ids and etag but no path. Polling is the primary file-change trigger in v1; SSE only speeds it up.
- WebDAV preconditions: `If-None-Match: *` on PUT is ignored (204, the file is overwritten); `If-Match` on PUT is
  enforced but returns 409 (treat 409 and 412 as conflict); `If-Match` on DELETE is ignored (204); `Overwrite: F` on
  MOVE and COPY is enforced (412).
- Folder ETag and `getlastmodified` propagate: creating, modifying or deleting a file changes the ETag and mtime of its folder and of every ancestor (measured two levels deep, on 9.0.0-rc.1), so one depth-0 PROPFIND of a watch folder detects any change below it; `fakeocis` does the same.
- Decision: write tools stat before creating and refuse if the target exists, and `files.delete` PROPFINDs and compares
  the ETag to the approved one itself before deleting (deletes go to the oCIS trash); the remaining race window is an
  accepted residual risk.
- Decision: no new notification channel (no email, webhook or oCIS notification hack). When the agent pauses itself, the
  reason is surfaced only inside the extension (status endpoint, banner, audit log).
- oCIS has no per-user notification create API (only admin or secret gated global notifications).

## Persistence

- Operational state lives in SQLite (`internal/store/sqlite`, pure Go) behind `store.Store`; `ocis-agent migrate` applies the embedded migrations, and start-up does too. Restore a backup with the sidecar stopped: copy it to `<data dir>/agent.db`, delete `agent.db-wal` and `agent.db-shm`, and start with the same `AGENT_MASTER_KEY` (sealed secrets need it; a wrong key fails at start-up). Behaviour is specified by the suite in `internal/store/storetest`; a new store implementation must pass it unchanged.
- The audit log is append-only and hash-chained per user (`internal/audit`). Never UPDATE or DELETE `audit` rows; a database trigger rejects it. Known limit: `VerifyAudit` cannot detect removal of the tail of a user's chain; anchoring the chain head outside the database is future work. Add events with `Tx.AppendAudit` in the same transaction as the state change they describe; its kind must be an `audit.Kind*` constant (anything else is `ErrInvalid`).
- Job leases: one running job per user. Every worker write (`SaveCheckpoint`, `AppendStep`, `RenewLease`, `ReleaseJob`) carries the lease fence, which only grows and is kept after release or reap. A voluntary release (back to queued or waiting_approval) refunds the attempt, so attempts count crashes, not approval pauses. Treat `ErrFenceLost` as "stop working on this job now". `Job.Runs` counts every claim and is never refunded; a runner must cap it and release to queued with `RequeueJob` and a delay.
- Secrets are sealed with `internal/secrets` (AES-256-GCM, per-use nonce, DEKs wrapped by the master key from `AGENT_MASTER_KEY`). Pass a domain-separated `aad` such as `app_token:<user id>` (not the bare user id) so a ciphertext cannot be moved to another context. Never store or log token values, DEKs or the master key.
- `InTx` and `View` are not re-entrant: never call the store, `secrets` or `queue` from inside the callback (seal before the transaction). Start-up calls `secrets.Init`, so a wrong master key fails fast.
- Errors: input validation failures match `store.ErrInvalid` (map them to client errors); `store.ErrExpired` means an approval was decided after it expired.
- Approvals leave `pending` only through `DecideApproval` (the user's decision; it checks expiry and the arguments hash), `ExpireApprovals` or `ExpireEndedJobApprovals` (approvals of ended jobs are settled to `expired` by `Gate.SettleEnded`, pending and approved only, never executing). The worker moves them with `TransitionApproval` (compare-and-swap on the legal edges only). A job waiting for approval resumes with `ResumeJobIfSettled` once nothing is pending; approved actions are executed after it resumes.
- Execution protocol for side effects: transaction A = `AssertLease` + approval approved->executing + `BeginIdempotent`; make the call outside any transaction; transaction B = `AssertLease` + `FinishIdempotent` + approval executed/failed/unknown + `AppendAudit` + `AppendStep`. A record still `started` after a crash means the outcome is unknown: reconcile it (the scheduler's `ReconcileOrphans` lists only records of ended jobs, `ListStartedIdempotentOfEndedJobs`) and never re-run blindly.
- Same-transaction rules: `InsertApproval` with `ReleaseJob(waiting_approval)`; `DecideApproval` with its `approval_decided` audit event and `ResumeJobIfSettled`; `ExpireApprovals` with `ResumeJobIfSettled` for every returned ref (refs are returned once, so a split strands the job). Idempotency keys are server-derived (job id, call id, args hash), never user-supplied.
- Model preference: `Policy.Models` maps a task kind (`store.ModelTaskChat`, `store.ModelTaskProactive`; `store.ModelTaskFor(trigger kind)`) to a model id. The store only checks the id's shape, so the API must check `llm.Catalog.Has` when setting one and the runner must use `Catalog.Resolve`. Always start from `GetPolicy` when changing a policy: a `Policy` built from scratch and put clears the preferences.
- Pause: the user's own pause is sticky; automatic reasons are ranked (`PauseSupersedes`); `ClearPause` clears only the reasons the caller names; queued jobs of a paused user are not claimed.

## oCIS access and memory

- `internal/ocisclient` is the only code that talks to oCIS. Every call takes a `Creds` (`AppToken(loginName, token)` or `Bearer(oidc)`); credentials, token values and token hashes are `Secret` values that print as `[redacted]`. `Creds` holds its secret behind a pointer, but a bare `Secret` in an unexported struct field still prints in clear, so hold credentials as `Creds`. Errors carry method, URL path and status only, never query strings or bodies, and redirects are not followed. Use `errors.Is` with its sentinels (`ErrNotFound`, `ErrPrecondition`, `ErrExists`, `ErrMalformed` for an untrustworthy PROPFIND response, ...). The login name for Basic auth is Graph `onPremisesSamAccountName`, not the user id.
- oCIS quirks live in `ocisclient` and `ocisclient/fakeocis` (an in-memory oCIS with the same quirks and fault injection): `Put` with `If-Match` maps 409 or 412 to `ErrPrecondition` (a 409 without it is `ErrNotFound`, a missing parent), `Get`/`Put` fail closed when oCIS sends no ETag, `Get` waits out a 425 (oCIS still postprocesses a fresh upload, also right after our own PUT; `fakeocis.SetPostprocessing`) for about 3s and then fails with `ErrTooEarly` (the API answers 503 `unavailable` with `Retry-After: 5`; error bodies are drained so the retries reuse the connection), `Move`/`Copy` never overwrite, `Delete` ignores `If-Match`, and `DeleteToken` takes the listed hash; callers confirm the delete through `ListTokens` (an already-gone hash is a 500). Tests of tools and memory use `fakeocis`; add a quirk to the fake whenever a new one is measured.
- Credentials (`internal/auth`): `Validator` accepts a bearer only if oCIS itself accepts it (Graph `/me` and the drive lookup, a 401/403 of either is a rejection; cached 60s, also capped by the token's `exp`; concurrent validations of one token share one lookup; `Known` remembers accepted tokens for up to 12h, at most six per user and 4096 in all, and forgets a rejected one); `User.Name` is the LOGIN name (Basic auth needs it). A new token's label is recorded (`AddTokenLabel`) BEFORE the create request and the swap transaction never adds it again; a refused create (401/403) closes its label, an UNCERTAIN failure (timeout, 5xx, lost response) that finds no token keeps it open (it may still land). `Renew` deletes the old token only after the new one is verified and stored; `Enroll` deletes superseded tokens right after its commit. `Sweep` flags (`token_anomaly` pause; audit holds the COUNT only, never labels) a token with our prefix whose label is unrecorded, recorded-and-closed, or a second token under the current label, and never deletes those automatically; it deletes orphans (open, non-current labels with a live token) at once and closes open labels with no token only after a 5-minute grace. `Enroll`, `Revoke`, `RevokeAll` (incident) and `Unenroll` take the user's bearer; the caller derives `userID` from the validated bearer and the revoke functions verify with Graph `/me` that the bearer belongs to `userID`; renewal and the sweep use the app token, never the bearer. Confirm a delete by listing again (an unknown hash is a 500). Call `HandleUnauthorized` when oCIS answers 401 for the app credentials (it re-checks the stored credentials with Graph `/me` and does nothing for a still-working token), `Seen` on every authenticated user request (clears only the dormant pause), and `DueForRenewal` + `Renew` (`RenewDue` is the same selection as one call), `Sweep` and `PauseDormant` from the scheduler (renewal and the sweep also run while the agent is paused).
- Approvals (`internal/approvals`): `Gate.Classify` decides from the tool's declared `Risk` and the call's arguments only (reads and memory writes run, everything else needs an approval, anything refused by the tool or invalid is denied; `auto_approve_write` is never read; raw arguments are capped before parsing). It returns the CANONICAL argument bytes, their hash and the idempotency key. `Request` refuses duplicate call ids, re-verifies hash, tool, key and risk (`ErrBadCall`) and re-counts the per-job cap (live approvals only, `ErrActionLimit`, `MaxActionsPerJob` <= 500) in its transaction; `Request`, `Decide` and `ExpireAndResume` are single transactions together with releasing or waking the job and the audit events; a decision on an ended job is `ErrJobEnded`. `Decide` must get the OIDC subject of the authenticated user as `decidedBy`. `Acknowledge` sets `acknowledged_at`/`acknowledged_by` of a settled approval whose `OutcomeUncertain` is true, with its `approval_acknowledged` audit event in one transaction (`NeedsVerification` = uncertain and not acknowledged); it never changes the state, and settled approvals never move, so an acknowledgement cannot be overtaken by a reconcile. `Run`, `RunAuto` and `RunRead` recompute hash, key and risk before running: `Run` refuses a mismatch with `ErrTampered`; `RunAuto` and `RunRead` return `ErrBadCall` for a key, tool or risk mismatch and `ErrTampered` only for the hash. `Run`/`RunAuto` are transaction A (lease, approval approved->executing, idempotency begin), the external call, transaction B (finish record, approval, audit, step); an existing record or an executing approval is reconciled via the tool, never run blindly; an unknown outcome is stored as idempotency failed with `{"outcome":"unknown"}` and the approval `unknown`. For a record left by an earlier attempt, a Retry verdict is honoured only after `Config.RetrySettle` (2 min) since it started, otherwise the outcome is unknown. A call interrupted by a cancelled ctx after transaction A (outcome not known) stays open (record started, approval executing): the next `Run` or `RunAuto` of the still-active job reconciles it, and `ReconcileOrphans` (called by the scheduler with now minus `CallTimeout` (5m) minus `RetrySettle` (2m); it lists ended jobs only, clamps `olderThan` to now minus `RetrySettle` and stops when ctx ends) covers ended jobs and never executes (Retry becomes failed, "not run"; a 401 or a failing env stays in `Errors` with the record open, but a user without usable credentials (`auth.ErrCredentialInvalid`, `store.ErrNotFound`) or a record older than `Config.OrphanGiveUp` (24h) is settled unknown). A lost lease still records the known outcome, returns a nil error and writes no step. Every effectful tool must be idempotent at the tool level or return Unknown (never Retry) from `Reconcile`. On `ErrNotApproved` from `Run` the runner re-reads the approval: terminal means call `Run` once more for the stored outcome, rejected means report it to the model as rejected, pending is a bug. `Outcome.Err` and errors from `Classify`/`RunRead` may match `ocisclient.ErrUnauthorized`: report them to `auth.HandleUnauthorized`; they are never shown to the model. The runner derives call ids from its own step sequence and runs tool calls of a job one at a time.
- Tools (`internal/tools`): a tool has `Prepare` (validate, preview, `TargetETag` of an existing target; no side effects), `Execute` (the call, with the approved `TargetETag`) and, if it has side effects, `Reconcile` (after a crash: Done, Retry, Failed or Unknown). Tools report a `Risk` and never decide policy; they get an `Env` built on the server (plain personal-drive id, credentials, budgets), so no argument can name a drive or user, and unknown JSON fields are errors. `parse` and `Canonicalize` also reject duplicate or case-variant JSON keys at any depth, non-object arguments, nesting deeper than 32 and objects with more than 256 keys, and `cleanPath` rejects control, line-separator and bidi characters, so what executes is what was approved; `ArgsHash` and `IdemKey` are computed only in `internal/tools`, and the gate must cap the raw argument size before parse or hash. Anything read from oCIS goes into `Result.Blocks` (untrusted, to be fenced), never into `Summary` or refusal text (refusal texts may echo model-supplied paths unfenced: model output, not file data); treat `Result.Diff` as untrusted too. `files.recent_changes` lists only `Env.WatchFolders` (a snapshot of the policy's watch folders taken at every claim; arguments can only narrow them, overlapping ones are walked once, reserved paths are never listed) through `ocisclient.Walk` (depth-1 PROPFINDs, at most 4 levels, 5000 entries, 200 requests and 2 minutes per call), newest first, and counts its block against the read budget; a missing, forbidden, too large or malformed folder is skipped and counted, an entry with an unusable name (a C0 control) is dropped and counted without hiding its siblings (`List` stays strict), and names in listing blocks escape line-breaking, bidi and invisible characters as `\u{XXXX}`. Write tools refuse the root and every `memory.IsReserved` path (source and destination) in `Prepare` and `Execute`; overwrite sends `If-Match` with the approved ETag, delete compares the ETag itself. `memory.read` stats before reading and calls `memory.Service.Forget` if its content cannot be handed to the model, because a cached ETag unlocks `memory.write` replace: the runner must `Forget` every `memory.read` result that never reaches the model (a `RunRead` error, a failed save, a truncated block), and only the job runner may call the memory tools. `memory.write` is auto-allowed (no approval screen), so the runner must record its `Result.Diff` in the activity feed. A 401 from oCIS is returned wrapped: report it to `auth.HandleUnauthorized`.
- LLM (`internal/llm`): `Provider.Complete` takes a validated `CompletionRequest` (dotted lower-case tool names, which the OpenAI client maps to `__` on the wire) and returns the model's message, `Usage` and a `StopReason`; tool-call `Arguments` stay a raw string for the gate. Treat everything it returns as untrusted. Never act on a `StopLength` response's tool calls (arguments may be cut off). Before a decoded assistant message goes back into the transcript, rewrite every `ToolCall.ID` to the runner's own transcript-unique id (the client invents `call_<i>` per response and `Validate` refuses duplicate ids). Provider errors are sentinels without bodies, URLs or keys: `llm.Retryable` (rate limit, outage) means requeue with a delay, `ErrAuth`, `ErrRejected`, `ErrMalformed`, `ErrTooLarge` and `ErrInvalid` do not, a cancelled context is a context error. The client only talks to the one configured https base URL (http only for loopback), never follows redirects, and checks the host allow-list. Keys are `llm.Secret`. Models: the operator's `llm.Catalog` (`AGENT_LLM_MODEL` default plus `AGENT_LLM_MODELS`) lists what users may choose; a user's choice per task kind is `Policy.Models` (`store.ModelTaskFor(job.TriggerKind)` picks the kind) and the runner must pass it through `Catalog.Resolve` before setting `CompletionRequest.Model`; an API that sets it must check `Catalog.Has`. `AGENT_LLM_*` are optional until the worker role needs them; `llmtest.New` scripts a provider for tests. `AGENT_LLM_TIMEOUT` (default 120s, 10s..30m) bounds one non-streaming call, response included (the runner adds no shorter deadline; a timeout is `Retryable`, so a slow local model needs a larger value). `AGENT_LLM_REASONING_EFFORT` (`none|low|medium|high`, unset sends nothing) is sent as `reasoning_effort`.
- Memory (`internal/memory`) is untrusted data under `/.ocis-agent/memory/`. `Write` of an existing file needs a prior `Read` (cached ETag per user, `ErrNotRead`) and fails with `ErrConflict` if the user edited it meanwhile; a file the user deleted drops its cached ETag on `Read`, so `Write` can recreate it. The ETag cache is per user and spans jobs, not per reader (known limit; the real fix is a base ETag for `Write` or a per-job cache): only the job runner may use `Read`. The memory excerpt and UI/API reads use `Peek`, a non-caching `Read` (same names, limits, text check and errors; never stores or drops an ETag, so no `Forget` is needed): seeing a file in the excerpt never unlocks a replace, which always needs the model's own `memory.read`. `Append` re-reads and retries. File tools other than `memory.*` must refuse paths for which `memory.IsReserved` is true (path-only: address the personal drive by its plain id, and check both source and destination of MOVE/COPY). Pass a `Budget` per job to cap memory writes, and record `Change.Diff` in the activity feed.
- Agent runner (`internal/agent`): `Runner.Run` runs one claimed job. The checkpoint is the transcript (the Goal as the first user message, after the conversation prefix of a chat job; over 1 MiB the job fails), and every provider call id is rewritten to the runner's own `c<N>`. At claim `Job.Runs` over `MaxRuns` fails the job; before every model turn come the step limit and the prechecks from the database, in order: kill switch (requeue at claim, else cancel), pause (requeue), credentials (invalid fails; fresh ones replace the env's), the daily budget `store.DailyBudget(DailyTokens, AGENT_USER_DAILY_TOKENS)` (stored 0 or above the operator's cap is the cap, the value the status shows; reached fails, for non-chat jobs already at 80% of it (`store.BudgetReached`); the day resets at UTC midnight and one model call may overshoot it). Kill switch, pause and credentials are checked before every model turn and every tool call; a running call is not interrupted and its batch's remaining approvals stay `approved` (resumed at the next claim after a pause; left live on a job the kill switch or invalid credentials ended). The model is `Catalog.Resolve` of the policy's choice for `ModelTaskFor(trigger)`; the system prompt carries the fenced `Peek` excerpt of `profile.md` and `projects.md`. `processCalls` is idempotent per call id and handles fresh turns, approval resumes and crash resume: read -> `RunRead`, memory write -> `RunAuto` (its diff audited as `memory_changed`), approve -> one `Gate.Request` batch at the end of the turn (over the action limit the whole batch is denied), deny -> refusal text plus a `policy_denied` audit event. Job errors and audit details are fixed `Reason*` constants, never provider or oCIS text. Env budgets (reads, memory writes) are per job and fresh per claim. `Run` returns nil once it released the job and an error while the job may still be running (lost lease or conflict wrapped, a context error as is, anything else the caller requeues). The Goal reaches the model as the user's own instruction, so goals of proactive jobs must never embed file names or other untrusted text: they are exactly `store.ProactiveGoal(trigger kind)` (`schedule`, `file_event`, `manual`). Live approvals of a job that ended stay until the scheduler's `Gate.SettleEnded` expires them. Around a freshly `approved` call (never a reconcile or a stored outcome) the runner calls the optional `Deps.OwnWrites` (`scheduler.OwnWrites`) with `tools.TargetPaths` of its arguments: it checks the watch folders with a baseline that contain them (the poll's `checkFolder`) before, and after a Done outcome compare-and-swaps `cursors.watch_etags` from that value to the new one in one transaction (never touching a pending change), so the agent's own writes do not start a `file_event` review; best effort, outside the executor's transactions (a crash or a failed check only yields the follow-up review).
- Worker (`internal/agent`): a `Worker` claims one job at a time and renews its lease every third of the queue's TTL (it takes the period from `Queue.LeaseTTL`; a renewal error other than a lost lease is retried, but a whole TTL without a successful renewal counts as lost). A lost lease cancels the job's context; shutdown requeues the job after `Config.ShutdownRequeueDelay` (keep it >= `approvals.Config.RetrySettle`, default both 2m); a panic or another runner error requeues with backoff until the runs cap, then fails it; while the kill switch is on it claims nothing; it logs ids and fixed outcomes only. With `WorkerConfig.JobContext` set, the context given to `Run` controls claiming only (the worker stops claiming and returns once its running job, still renewed, has finished) and the end of `JobContext` cancels the job (the shutdown requeue) and stops claiming too; unset, jobs run under the `Run` context. `internal/app` wires the workers, the scheduler and the REST API (next bullets).
- Process and scheduler (`internal/app`, `internal/scheduler`): `AGENT_ROLES` (default `api,worker`) selects `api` (the REST API on `AGENT_HTTP_ADDR`: header timeout 10s, idle 120s, 64 KiB headers, no write timeout since the API sets per-request deadlines; it needs no LLM, an unconfigured catalog is empty) and `worker` (workers plus the scheduler, which needs `AGENT_LLM_*`; `Build` checks LLM and model catalog before writing anything). `Build` wires store, secrets, auth, memory, tools, gate, queue, API server, runner, workers and scheduler. Shutdown on SIGINT/SIGTERM: (1) stop claiming and the scheduler, `/readyz` goes 503, close `api.Deps.Stop` (event streams end), the API listener stops gracefully (up to 10s); (2) wait up to `AGENT_SHUTDOWN_DRAIN` (default 30s, counted from the signal) for running jobs; (3) cancel them so the workers requeue after `ShutdownRequeueDelay`. The container grace period must be >= `AGENT_SHUTDOWN_DRAIN` + 15s (45s with defaults; the Kubernetes default of 30s is too short); close the store only after `Run` returns. Run exactly ONE process with the worker role per database; an api-only process runs no maintenance (no renewal, expiry or dormancy) and logs that once. The store itself refuses to hand out work (`ClaimNextJob`) while the database kill switch is on or the user is paused; `ocis-agent killswitch on|off|status` flips the database flag (workers notice without a restart; `AGENT_KILL_SWITCH=true` forces it on) and refuses a missing database file instead of creating one (it still needs a well-formed `AGENT_MASTER_KEY` and `AGENT_OCIS_URL`, since `config.Load` runs first, and applies pending migrations). Scheduler (`scheduler.Scheduler`, 1s tick): first the database-only tasks: reap expired leases every lease TTL/2, `ExpireAndResume`, `Gate.SettleEnded` (approvals of ended jobs) every minute, `PauseDormant` hourly, the `proactive` task every minute (users from `ListProactiveDue`, a stable rotation, at most 50 started per run: eligibility is `store.CheckProactive` (enrolled, enabled, kill switch off, not paused, outside the UTC quiet hours, no live proactive job, under `AGENT_PROACTIVE_DAILY_JOBS`, below 80% of the token budget), `store.StartProactive` inserts the `schedule` job with its fixed goal, moves `cursors.last_sweep_at` and audits `proactive_started` in ONE transaction re-checked inside; a user enabled without a last sweep gets it set to now first, and `PUT /settings` enabling sets it too, so the first sweep is one interval later; a skip keeps `last_sweep_at` and the user is checked again after an in-memory wait (live_job 2m, paused 5m, budget 15m or UTC midnight, daily_cap UTC midnight, quiet hours their end; it only saves work, every check reads the database), and `store.AuditProactiveSkip` audits only live_job, daily_cap and budget, on a change of reason (the user's newest proactive event in the chain) or once per 24h, never paused or quiet hours; nothing at all while the kill switch is on); then the oCIS-bound ones, each under a 2m deadline (`TaskTimeout`; watch 1m, so a hung oCIS delays the database tasks by up to 7m), renew and sweep stopping at the first unavailable item: `ReconcileOrphans` (only records of ended jobs; active jobs reconcile themselves) and token renewal every minute, the token sweep (up to `Batch` calls per run) per user every `AGENT_TOKEN_SWEEP_INTERVAL` (15m); the `watch` poll every 10s (users from `ListWatchUsers`: enabled, not paused, with watch folders; rotation, at most `AGENT_WATCH_MAX_POLLS_PER_TICK` users per run, 4 in parallel, each every `AGENT_WATCH_POLL_INTERVAL`, nothing under the kill switch): a depth-0 `Stat` of each watch folder with the app token compared with `cursors.watch_etags` (the root, which holds the agent's own folder, is listed one level deep without it and digested instead, so memory writes never count); a new folder is a baseline, a vanished one loses its baseline, any other error skips the folder, a 401 goes to `Auth.HandleUnauthorized` and discards the user's poll; a change sets `watch_dirty_since`/`watch_changed_at`, the user is polled again at the debounce, and once quiet for `AGENT_WATCH_DEBOUNCE` (or 10m after the first change) `store.CheckProactive` + `store.StartProactive(file_event)` run in the transaction that clears it; a refused change stays pending, is retried at the next poll and goes to `store.AuditProactiveSkip`; a poll in which every folder failed never fires a pending change; changing the watch list (in `PUT /settings` or seen by the poll) drops a pending change, and enabling proactive work resets the watch state; the run has a 1m deadline of its own and records each user's poll as soon as it finishes (in its own short transaction), and a poll the deadline cut short is discarded and retried at the next run; with `AGENT_SSE_ENABLED` the database-only `sse` task (every 30s, before reconcile) keeps one notification stream (`ocisclient.StreamEvents`, app token, `Env` per connection) open for each of the first `AGENT_SSE_MAX_SUBSCRIPTIONS` `ListWatchUsers` with a valid app token, reopens it when the token label changes, closes the rest (and all under the kill switch), and `Close` (deferred by `Run`) waits for them; reconnects back off 1s..5m with jitter (a 401 goes to `Auth.HandleUnauthorized` and waits the longest); a `folder-created`/`postprocessing-finished`/`item-renamed`/`item-trashed` event only pokes the user, and the next watch run polls poked users that are still watched first (at most once per 30s each, within `PerTick`), with the usual debounce and gating; event data is never read or logged, and the agent's own writes cannot be told apart by `initiatorid` (it acts as the user), so `OwnWrites` keeps them from counting; maintenance keeps running while the kill switch is on or users are paused (proactive enqueueing does not), and a failing task only logs. The debug listener (`AGENT_DEBUG_ADDR`, default `:9301`, `off` disables) serves only `GET /healthz` and `/readyz` without auth, never `/agent*`, and stays up until the end. A log line carries ids, counts and fixed categories, never an error's text. `Gate.Decide` does not wake the queue itself: its caller calls `Queue.Wake` (the decision handlers do), like `Enqueue`.
- REST API (`internal/api`, base `/agent-api/v1`, plus unauthenticated `GET /agent-api/healthz`): every request first gets recover, a request id, security headers and a 30s read/write deadline (also unmatched paths and healthz; a route may set its own, the export 5 min). Then, in order: the per-IP failed-login bucket (IPv6 by /64; a token the validator has neither cached nor `Known` reserves a token before reaching oCIS, refunded unless the token was rejected or the client hung up), for state-changing methods `Origin` equal to `AGENT_ALLOWED_ORIGIN` and `Sec-Fetch-Site` same-origin if sent, the bearer validated by oCIS through `auth.Validator`, the per-user rate limit (`AGENT_API_RATE`, `AGENT_API_BURST`), `Seen` (at most once a minute per user, also for users who never enrolled), bodies of at most 64 KiB (settings 128 KiB, memory 400 KiB, chat messages 32 KiB, `withMaxBody`) and 2048 values with strict JSON (exact-case keys, unknown fields such as `auto_approve_write` are 400; action endpoints take an empty body or `{}`). List routes refuse malformed or unknown query parameters (400). Identity comes only from the validated bearer and every lookup is scoped by it (another user's ids are 404, an unknown or foreign cursor 400); `decidedBy` is the Graph user id (the bearer is opaque, there is no separate subject). Errors are fixed codes and messages, never upstream or store text. Untrusted text must be rendered as plain text: goal, answer, summaries, rationale and audit detail are capped in views, but `args`/`preview` are returned as stored (up to 2 MiB each) and the export's detail is uncapped. Lists page by keyset within an 8 MiB response budget; clients follow `next_cursor` until it is null (a page may be short, even empty, and still carry one). `GET /audit` takes `order=asc|desc` (default asc; a desc cursor is `d<seq>`, refused in asc and vice versa; a cursor of either order must name a record of the caller's log, else 400, and since the log is append-only a cursor once issued stays valid) and `kind` (one of the `audit.Kind*` constants, which every emitter uses; anything else is 400); the export stays ascending. `pending_approvals` in the status is an exact count of live jobs' approvals, while `?state=pending` also lists ended jobs' approvals with `job_ended: true`. Job views carry `trigger_ref` (a chat job's conversation id, empty for other triggers), `ended_at` (`jobs.ended_at`, set by the transition that ends the job; null while live) and `tokens_in`/`tokens_out` (sums over the steps, computed in the list query, no query per row). A decision is bound to `args_hash` (409 `stale_arguments`) and wakes the queue. `POST /approvals/{id}/acknowledge` (empty body or `{}`) records that the user checked an uncertain outcome (`needs_verification`: state `unknown` or an unreadable or unknown stored result); the state stays, nothing wakes, a repeat returns 200 with the same view, a certain or unsettled outcome is 409 `not_acknowledgeable`; `?needs_verification=true` (the only value; the state then defaults to all) lists only unacknowledged ones, examining at most 2000 candidates per request (`ListApprovalsToVerify`; a page cut there may be short or empty and carries a cursor). Every reader of a stored outcome decodes it with `store.DecodeOutcome`. Enrol, renew, revoke, revoke-all and `POST /proactive/run` share ONE 5s per-user cooldown (unenroll is only rate-limited); `POST /proactive/run` (empty body or `{}`) starts a `manual` review with the same `store.CheckProactive` checks minus quiet hours and interval in the inserting transaction (202 with the job view, 409 `not_enrolled`, `proactive_disabled`, `kill_switch`, `paused` (`credentials_invalid` for a `credential_*` pause), `live_job`, `daily_cap` or `budget`) and counts as the last sweep; audit verify runs once per user and twice per process, export once per user and eight times per process with a 30s write deadline per page (429 with `Retry-After`; HEAD is 405). The verify result carries `checked` (events that verified) and, when broken, `broken_at` (seq of the first failing event); `message` stays fixed text. `POST /pause` never replaces a `credential_*` or `token_anomaly` pause; resume clears only `user` and `token_anomaly`. A new user's stored `DailyTokens` is 0, which means the operator's `AGENT_USER_DAILY_TOKENS` (also shown to users not yet enrolled; `PUT /settings` with `daily_tokens: null` returns to it); settings cannot exceed it, pick a model outside the catalog or touch `auto_approve_write`. The audit export aborts the connection on a failure.
- Chat, memory and events (`internal/api`): tables `conversations` and `messages` (`0011_chat`); the API writes only `user` messages, the runner writes `assistant` (answer, capped 64 KiB) and `system` (fixed `Reason*` text) messages in the transaction that releases the ended job (deleted conversation tolerated). A send is ONE transaction: enrolled, own conversation, the live-chat-job cap (5, 429 `too_many_pending`), the daily chat cap (1000 chat jobs per UTC day, 429 `limit_reached` with `Retry-After` until UTC midnight) and the daily token budget (429 `budget_exhausted`) counted INSIDE it, then job (`TriggerChat`, ref = conversation, Goal exactly the user's text), message (with its job id), title fill and the `chat_message` audit event, then `Queue.Wake`; it is accepted while paused or killed (`agent` in the 202 says why nothing runs; an api-only deployment never runs jobs). Limits: 200 conversations (409 `limit_reached`), 1..8192 bytes of text without control characters other than tab/newline/CR, 1s per-user cooldown that a refused send also uses. The prefix (written to the checkpoint at the first claim, never into the system prompt): up to 20 earlier user and assistant messages of the conversation (later questions and system messages never count), each capped at 4 KiB, oldest dropped until 24 KiB; a question counts only if its job failed or succeeded (queued, running, waiting_approval and cancelled ones are not replayed, so they are not answered twice), answers without their question are dropped, consecutive user messages are merged and a trailing unanswered question is joined with the Goal (the Goal row stays exact). User message views carry the answering job's `{id,state,error}`, since jobs ended outside the runner (cancel, reaper) write no message. Deleting a conversation removes its messages, cancels its live jobs and audits `conversation_deleted` in one transaction; the goals and checkpoints of its jobs stay visible in `GET /jobs`. Chat jobs use the app token (interactive OIDC tokens for tools are not implemented). Memory routes (`GET /memory`, `GET/PUT /memory/{name}`, `notes/{slug}`, `POST /memory`; they do not require enrolment) use the user's bearer and only `Peek`/`Replace`/`Create`, never the ETag cache (so a user edit makes the model's next replace fail until it reads again); PUT needs `If-Match` (428 without, 412 when changed), POST on an existing file is 409 `already_exists`, a file over `MaxFileBytes` is returned cut with `truncated` and `editable:false`, one over `MaxReadBytes` is 422 `file_too_large`, and the body limit is 200 KiB (a 64 KiB file of control characters escapes to 6x and may get 413). `memory_edited` audits the name and a 1500-byte diff (kept permanently) after the write, under `context.WithoutCancel`; a PUT with an uncertain outcome is not audited. Every request body rejects invalid UTF-8 and unpaired surrogate escapes (`decodeBody`). `GET /events` (SSE) sends `ready`, then `changed` with kinds only (`jobs`, `messages`, `activity`, `settings`) from a 2s database poll (works across processes, api-only too), `: ping` every 25s and `bye` at the lifetime (random 55-65 min per stream) or on `Deps.Stop` (new streams then 503); a failed poll is skipped and the stream ends with `bye` `unavailable` after 3 in a row; the bearer is validated only at connect, so an open stream outlives a revoke or unenrol by up to 65 min (kinds only, same user); caps `AGENT_API_STREAMS_PER_USER` (3) and `AGENT_API_STREAMS_TOTAL` (200), over them 429 with `Retry-After: 5`; no `id:`/`Last-Event-ID`: clients refetch everything on every `ready`, poll the REST resources after a 429 or 503 from `/events`, and refresh fully every ~60s, since some changes move no mark (an older message deleted, the kill switch) and a same-millisecond change can be missed. `Deps.EventsPollForTest` is a test-only hook.
- Frontend (`frontend/`): `index.ts` wires the oCIS Web runtime (access token, backend URL, toasts, modals) into `platform.ts`; components reach it only through the platform, and navigate only with the host's `$router` and global `<router-view>`/`<router-link>`; `api/` is the only code that talks to `/agent-api/v1`; the token is read per call and never stored or logged. Never import `vue-router` at runtime (it is not externalised, and a bundled copy does not see the host's router; type imports are fine) and keep `vue3-gettext` on the host's major (2.x). Enumerations in `api/types.ts` are open (`X | (string & {})`); write case labels and compared literals as `'v' satisfies X` so a typo fails `check:types`. Server text (goals, answers, titles, summaries, args, previews, audit detail, memory) is rendered as plain text only through `visibleText`/`TextBlock`/`JsonBlock` (a unit test fails on `v-html`/`innerHTML` in non-spec sources). The events client reads `/events` with fetch, refetches everything on every `ready`, polls after a 429/503 and refreshes fully every ~60s. `stores/agent.ts` holds status, approvals and settings (a `jobs`/`activity` change rereads only the first page of each approvals list, title count from `status.pending_approvals` when cut off; every page on `ready`, a poll or a user refresh); the screen stores (`chat`, `jobs`, `audit`, `memory`) `subscribe` to its change kinds only while their screen is mounted (on a change `chat` and `jobs` reread their first pages, `memory` rereads its list and the open file on `activity`, `audit` reads newest first (`order=desc`, kind filtered by the server) and new events forward after the log's newest seq, keeping at most 1000), and reset when the session ends; a screen syncs its store's session in setup, before it relies on the store's data (`syncSession`, memory via `refreshList`). Screens: enrol, chat, approvals, tasks, activity, memory, settings (status banner in the layout; the app root opens Approvals while approvals are pending, else Chat). The approvals to verify are the `needs_verification=true` list, and "I checked" acknowledges one; a chat job links to its conversation (`trigger_ref`). Not built: token streaming, per-message edit or delete, conversation search or export, memory delete.
